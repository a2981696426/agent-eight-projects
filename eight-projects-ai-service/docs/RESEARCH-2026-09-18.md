## 二、两个智能体项目教程的分析与可借鉴点

### 2.1 SpringAI + 多 Agent 企业级 AI 内容创作平台（codefather 2031299079576838146）

**优势**：选题贴真实业务（自媒体图文）；5 个智能体分工明确（标题 → 大纲 → 正文 → 配图分析 → 并行配图）；三阶段 Human-in-the-loop（标题选择、大纲编辑）；StateGraph 工作流串行/并行；7 种配图策略（策略模式）；SSE 流式让用户看到创作过程；Stripe 会员 + 配额；AOP 注解自动记录智能体执行日志并统计耗时/成功率；异步任务 + 线程池；Docker Compose + Nginx 一键部署。

**业务流程**：注册登录 → 输入选题 → 阶段 1 标题（用户选/补充）→ 阶段 2 大纲（用户编辑/AI 优化）→ 阶段 3 正文 + 配图（3 个智能体协作）→ 查看/导出。

**功能模块**：用户、文章、智能体调度、配图策略、支付/配额、统计。

**技术选型**：Spring Boot 3.5 / Spring AI Alibaba 1.1 / 通义千问 / MyBatis-Flex / MySQL / Redis + Redisson / Stripe / COS；Vue 3.5 + TS + Ant Design Vue + Vite 7 + Pinia。

**可借鉴到本项目**：
1. **SSE 流式推送执行进度**——我们的九阶段天然适合逐阶段推送，把 8–14s 的黑盒等待变成可见进度（本轮实现）。
2. **AOP 式执行日志 → 统计**——我们已有 trace，本轮补 provider/阶段级统计（成功率、平均耗时、切换次数）进入健康接口与大屏。
3. **任务状态机**（ArticlePhaseEnum）——对应我们的会话 `controller/status` 与 trace `decision`，保持显式枚举。
4. **策略模式扩展点**——我们的场景包 + ToolRegistry 已是同构做法；新增售后能力 = 新场景包 + 工具。
5. **配额/会员**——客服场景对应"租户/坐席配额与限流"，列入后续。

### 2.2 Python 全栈 | AI 修图智能体（codefather 2099386518517915649，源码 github.com/yuyuanweb/ai-picture-editor）

**优势**：自然语言 → 结构化多步计划（LangGraph plan → verify → 执行）；**ToolRegistry 一处定义同时服务 Agent、服务端校验与前端展示**；**Provider 抽象层，Mock 与真实模型零成本切换**；ARQ 异步队列 + Redis Pub/Sub + SSE 推送长任务进度；HITL：单步直接执行、多步必须确认；revisionId 版本链撤销重做；Kahn 拓扑排序执行依赖；JWT httpOnly Cookie + 路由守卫；Docker 多阶段 + compose profile；pytest 覆盖含评测。

**业务流程**：文生图（异步任务 → 四宫格候选 → 进编辑器）；编辑器修图（同步工具毫秒返回 / 异步工具进队列 → 图片墙 → 采用）；Agent 对话修图（plan → verify（工具存在性/参数/依赖/环检测）→ 单步执行或多步确认 → 拓扑推进）。

**功能模块**：文生图、画布、Agent 对话、21 个编辑工具、区域选择、局部编辑、图层拆分、多步计划、用户认证、部署。

**技术选型**：Python 3.13 / FastAPI / SQLAlchemy 2 + Alembic / Pydantic v2 / LangChain + LangGraph / DashScope / SAM / rembg / ARQ / MinIO / PostgreSQL / Redis；React 19 + TS + Vite + Tailwind v4 + react-konva + Zustand + TanStack Query。

**可借鉴到本项目**：
1. **Provider 抽象层 + Mock**——本轮实现 `LlmRouter`：多 provider（主/备）、重试退避、熔断、自动切换，以及 **无模型时的规则降级**；Mock provider 让 e2e 不依赖外网也能跑通链路。
2. **服务端计划校验**——我们对模型输出已做引用白名单/动作许可校验，本轮把"提案动作 ∈ 场景包允许列表"之外的越权提案也记为风险信号（已具备）。
3. **单步直接执行 / 多步确认（HITL）**——对应我们的自治门禁：低风险白名单自动、其余人工确认；语义一致。
4. **异步队列 + SSE**——质检批量、VoC 分析、Benchmark 这类长任务后续改为后台作业 + 进度推送（列入待做，本轮先做执行链 SSE）。
5. **JWT httpOnly Cookie 认证 + 路由守卫**——本轮实现登录与三角色（管理员 / 坐席 / 质检分析）。
6. **Docker 多阶段 + compose**——本轮补 Dockerfile 与 docker-compose，API 直接托管前端构建产物。

### 2.3 两教程与本项目的关键差异

- 两教程都是**单租户创作型**产品，任务由用户主动发起、结果由用户验收；客服系统是**对外服务型**，多了"访客不可控输入 + 风险分级 + 人工接续 + 质检回溯"这一层，因此我们的自治门禁与分层可信度不能省。
- 两教程依赖 Redis/PostgreSQL/MinIO 等中间件；本项目坚持 `node:sqlite` 单进程零依赖，便于本机与小团队部署，代价是横向扩展能力弱——文档中标注为已知边界。

## 四、本轮据此推进的 Loop 清单

1. **执行链提速与准确率**：证据获取与知识检索并行；必填槽位缺失时不调用推理模型（模板追问，~1s 内返回）；推理提示精简；Benchmark 前后对比（场景/决策准确率、平均耗时）。
2. **模型高可用**：`LlmRouter` 多 provider（`.env` 配主/备）、指数退避重试（429/5xx/超时）、熔断器（连续失败 N 次 → 冷却 T 秒）、自动切换、**规则降级模式**（意图关键词规则 + 工具事实模板回复，强制人工确认并在 trace 标记 `degraded`）；`/api/health` 与 Agent Studio 展示 provider 状态与统计。
3. **执行链进度 SSE**：`POST /api/conversations/:id/messages/stream` 逐阶段推送；访客端与在线机器人页显示"正在识别意图…/正在查询订单…"。
4. **发布形态**：登录（httpOnly 签名 Cookie）+ 三角色（admin / agent / analyst）+ 路由守卫与接口权限；API 托管 `apps/web/dist`（单端口部署）；Dockerfile 多阶段 + docker-compose；会话结束自动后处理（小记 + 待办）。
5. **全量回归**：typecheck / 单测 / build / Playwright（页面零错误 + 真实模型流 + Mock 降级流）。
