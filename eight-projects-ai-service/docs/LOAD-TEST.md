# 压测记录（k6）

门禁（切片 0 P1）：200 并发访客下端到端 p95 ≤ 15 s、失败率 < 1%。脚本 `load/k6-chat.js`，每次迭代 = 新建会话 → 寒暄（规则）→ 物流查询（完整九阶段执行链）→ 读取会话。

## 2026-09-19 · 本机（Windows，Node 24，PGlite 进程内库，单 API 进程）

### peak：0→200 VU（60 s）· 持稳 200 VU（120 s）· 降 0（30 s），mock 模型（`LLM_MOCK=1`，测平台开销）

| 指标 | 结果 |
|---|---|
| 迭代 / 请求 | 5,216 次迭代 · 20,864 请求 · 97.4 rps |
| 失败率 | http 0.00% · 业务 0.00% |
| 寒暄（规则） | p50 714 ms · p95 973 ms · p99 1,404 ms |
| 执行链（mock 模型） | p50 723 ms · p95 986 ms · p99 1,408 ms · max 1,526 ms |
| API 进程 | RSS 390 MB → 760 MB（含内存库全部数据）；CPU 持续约 1 核满载（每 5 s 采样 CPU 时间 +5 s） |
| 门禁 | 全部通过 |

解读：mock 模型下时延几乎全是**平台开销**，200 VU 时单进程 CPU 打满，p50 从空载 ~20 ms 涨到 ~700 ms——瓶颈是单个 Node 事件循环 + 同线程运行的 PGlite（WASM，单线程）。生产形态（`pg` 连独立 PostgreSQL + API 双副本）会把数据库计算移出 Node 进程并把 CPU 容量翻倍；真实模型时延（下表）比平台开销高一个数量级，所以 200 并发的真实瓶颈在模型侧并发与限流，不在 4 核 8G。

### smoke：3 VU × 25 s，真实模型（DeepSeek `deepseek-flash`，8787 开发实例）

| 指标 | 结果 |
|---|---|
| 迭代 | 8 次 · 0.8 rps |
| 寒暄（规则，0 模型调用） | p50 21 ms · p95 43 ms |
| 执行链（意图 + 推理两次模型调用） | p50 8,402 ms · p95 12,257 ms · p99 13,351 ms · max 13,624 ms |
| 门禁 | 通过（p95 12.3 s < 15 s，余量约 20%） |

解读：完整执行链的真实时延由两次模型调用决定（与 Benchmark 记录一致）；p95 距门禁只有 ~2.7 s 余量，高峰期模型侧排队即可能越线。SSE 逐阶段进度已把"黑盒等待"变成可见进度，但门禁指标本身需要靠：① 更多场景走模板/规则短路；② 推理阶段更短的提示与输出上限；③ 备用 provider 分流。

### smoke：5 VU × 30 s，mock 模型

寒暄 p95 79 ms · 执行链 p95 27 ms · 0 失败（空载基线）。
